# 团团团：项目总结与宝洁八大问

> 用途：产品、运营、技术岗位面试复盘。以下内容基于当前代码和测试记录整理，真实微信点击联调仍需在开发者工具中完成，不把未验证结果表述为线上成绩。

## 一、项目一句话介绍

“团团团”是一个面向线下活动的 AI-LBS 微信小程序。用户用自然语言描述周末想参加的活动，系统通过 GLM 将需求解析为结构化条件，经过用户确认后，再根据活动事实库做硬条件过滤、确定性排序和可解释推荐；找不到合适活动时，用户可以选择地点并提交一条待审核拼团需求。

## 二、1 分钟项目介绍

我负责把一个只有页面原型的想法推进成可演示、可测试、可接入真实服务的微信小程序 MVP。项目包含 9 个页面和 5 个 Tab，前端采用原生微信小程序，后端采用 Django + DRF + SQLite，服务层接入 GLM，高德 Web API 用于地点搜索和地址解析。

产品上我把流程拆成两条主线：一条是“描述需求—AI 解析—确认条件—匹配活动—加入拼团—群聊”，另一条是“找不到—发布带地图位置的待审核需求”。技术上我重点处理了 Workflow 的不确定字段确认、事实约束推荐、推荐理由可追溯、名额一致性、JWT 权限、消息幂等和 API/演示双模式隔离。当前自动化证据包括 Node 18/18、后端 pytest 19/19、Mock 评测 40/40；真实 GLM 5 条受控冒烟中 1 条成功、4 条读取超时，不能外推为模型质量达标。

## 三、项目背景与目标

- **用户痛点**：线下活动信息分散，用户很难把“人数、时间、预算、距离和偏好”转成有效筛选条件。
- **产品目标**：降低找活动的表达成本，并让推荐结果可解释、可验证。
- **MVP 边界**：先维护明确的示例活动，由管理员维护正式活动；本轮不做支付、真实导航、RAG、公网部署和用户直接创建可加入活动。
- **关键约束**：API Key、微信 AppSecret 和高德 Key 只能在后端环境配置；API 模式失败不能静默回退演示数据。

## 四、我的主要工作

### 1. 产品和流程设计

- 将页面原型整理为 9 个可访问页面：首页、地图、发布、确认、匹配、详情、消息、群聊和个人中心。
- 设计“先确认条件，再推荐”的流程，避免 AI 直接生成价格、名额或活动事实。
- 为无匹配结果设计后续动作：调整条件，或提交带地点的待审核需求。

### 2. AI 需求解析和推荐

- 通过后端调用兼容 Chat Completions 的 GLM 接口，Prompt 版本为 `intent-v2`。
- 将 AI Workflow 拆成意图解析、Schema 校验、不确定字段标记、用户确认、事实过滤、排序和解释七个节点。
- 服务端校验 AI JSON，再由后端执行城市、时间、预算、距离、容量等硬过滤；价格、距离、名额和活动是否存在不由模型生成。
- 增加 40 条离线评测样本和 `evaluate_ai` 命令，记录字段准确率、偏好 F1、不确定字段召回率、硬过滤违规数和响应耗时。
- AI 超时时返回结构化错误；前端请求超时调整为 45 秒，避免模型响应较慢时显示 Django HTML 错误页。

### 3. 后端业务和权限

- 建立活动、拼团、用户、成员关系、收藏、消息和待审核发布需求模型。
- 使用 JWT 访问令牌和刷新令牌；加入、退出、收藏和聊天接口要求认证。
- 成员关系设置唯一约束；消息使用客户端 `client_id` 幂等，网络重试不会重复入库。
- 加入和退出在事务中完成，并校验活动状态、剩余名额和重复加入。

### 4. 地图和发布需求

- 高德 Web API 只由后端代理调用，提供地点搜索和地址解析，Key 不进入小程序。
- 发布页支持搜索地点、选择候选地点并保存名称、地址和经纬度。
- 地图页从示意图替换为微信原生 `<map>`，支持真实底图、缩放、拖动、旋转、指南针和活动标记。
- 用户发布内容进入 `pending` 待审核队列，不自动生成可加入活动，避免把未经审核的需求当成真实供给。

### 5. 工程质量

- 保留 `local-demo` 和 `api` 两种模式，分别隔离缓存和数据来源。
- 为加载、失败、重试、防重复提交和登录过期补充状态处理。
- 通过官方 WXML/WXSS 编译器和 Node/Django 自动化测试，持续更新执行状态文档。

## 五、关键 STAR 故事

### 故事 A：把页面原型推进为可运行 MVP

**S（情境）**：项目最初只有首页原型和零散页面想法，无法验证用户能否走完整流程。

**T（任务）**：在不破坏原有 AppID 和视觉方向的前提下，形成可以在微信开发者工具中运行的 MVP。

**A（行动）**：我先梳理用户主线，补齐 9 个页面和 5 个 Tab；把活动、拼团、成员、消息抽成独立数据层；再补导航封装、空状态、错误重试和页面回显。每完成一段就用 Node smoke 和官方编译器验证。

**R（结果）**：形成“需求输入—条件确认—匹配—详情—加入—聊天—个人管理”的完整演示闭环；Node 18/18、后端 pytest 19/19、Mock 评测 40/40 通过。

### 故事 B：处理 AI 超时导致的 HTML 错误

**S**：真实 GLM 调用在模型响应较慢时触发 `socket.timeout`，Django 调试模式把 HTML 错误页返回给小程序，用户看到整段 `<!DOCTYPE html>`。

**T**：让 AI 失败变成用户可理解、可重试的错误，并避免客户端提前断开连接。

**A**：我根据后端堆栈定位到 `socket.timeout` 没有被捕获，补充异常处理；前端过滤 HTML 错误内容；把后端模型超时设为 40 秒、前端解析请求设为 45 秒；用测试覆盖 API 错误路径。

**R**：错误从不可读的 HTML 变为明确的 AI 服务失败提示；本轮真实 GLM 冒烟若遇到读取超时会被记录为结构化失败，不会静默使用 Mock；API 适配与后端异常测试继续通过。

### 故事 C：设计“无匹配后发布”而不制造虚假活动

**S**：用户可能提出数据库中没有的需求。如果直接生成活动，会把 AI 推测误当成真实供给。

**T**：让用户仍然能继续表达需求，同时保证活动数据真实可控。

**A**：我设计了待审核 `PublishRequest` 模型，要求提交人数、时间、预算和具体地点；高德只负责地点搜索和地址解析；后台通过 Admin 审核后再维护正式活动；匹配空状态提供发布入口。

**R**：流程从“找不到就结束”变成“调整条件或提交需求”，同时不自动生成价格、剩余名额和可加入拼团，降低了产品诚信和数据一致性风险。

### 故事 D：把 AI 能力从“能调用”推进到“可评测”

**S**：只有模型调用和 JSON 校验，无法回答解析是否稳定、模糊表达是否被识别，以及推荐是否违反活动事实。

**T**：建立一套不依赖线上用户数据的 AI 产品验证方法。

**A**：我构造了 40 条覆盖完整、缺失、否定、比较和非法输入的需求样本；将解析拆成字段准确率、偏好 F1、不确定字段召回率，并对推荐结果增加硬过滤违规和事实解释一致性检查；Mock 回归与真实 GLM 对照使用同一套命令和报告格式。

**R**：Mock 评测核心字段宏平均准确率 100%、偏好 F1 0.963、不确定字段召回率 100%，硬过滤和事实解释违规均为 0。真实 GLM 5 条受控冒烟中 1 条成功、4 条读取超时；报告明确记录为部分可用和服务可达性问题，没有冒充模型质量结果。

## 六、宝洁八大问：模拟提问与回答

### 1. 请介绍一个你最有成就感的项目或成果。

**回答：**

我最有成就感的是把“团团团”从页面原型推进成可运行的 AI-LBS 小程序 MVP。最初页面之间没有完整数据流，也不能验证加入、聊天和错误处理。我先拆出用户主线和数据关系，再实现前端演示模式、Django API、GLM 解析、事实约束推荐和评测命令。过程中我用自动化测试约束质量，目前 Node 18/18、后端 pytest 19/19，Mock 评测 40/40；真实 GLM 冒烟中 1 条成功、4 条读取超时，我没有把小样本结果包装成模型质量结论。这个成果让我体会到，产品想法要真正有说服力，必须同时具备可操作流程、可验证数据和清楚的边界。

### 2. 请举例说明你如何承担领导或推动工作。

**回答：**

这个项目没有现成的后端和接口规范，容易陷入“先做页面还是先做服务”的争论。我把工作拆成页面骨架、数据模型、API 契约、AI 适配和验收证据几个阶段，给每个阶段设定可检查的结果，并持续更新执行计划。这样团队或后续协作者可以按接口和测试结果接手，而不是依赖口头说明。我的推动方式不是单纯分配任务，而是把目标变成可复现的交付物。

### 3. 请举例说明你说服别人接受你观点的经历。

**回答：**

关于“AI 找不到活动后是否直接生成拼团”，我主张先做待审核需求。我的依据是活动价格、名额和时间属于事实数据，不能由模型自由生成；如果直接生成，用户会误以为活动已经存在。于是我把方案拆成两个动作：用户可以提交需求，但只有管理员审核后才成为正式活动。这个方案既保留了转化入口，也保护了数据可信度，最终成为当前实现边界。

### 4. 请举例说明一次团队合作。

**回答：**

项目中前端页面、后端接口和测试必须同步，否则很容易出现字段不一致。我用 API 契约明确请求路径、字段和错误状态，前端服务层负责转换，页面只处理业务状态；后端测试则固定权限、重复提交和容量规则。这样合作时大家围绕同一份接口约定工作，减少了“页面看起来能点但接口不能用”的返工。

### 5. 请举例说明你解决复杂问题的经历。

**回答：**

真实 GLM 调用出现超时并返回 HTML，是一个跨越网络、Python 异常处理和小程序错误展示的问题。我没有只在前端隐藏错误，而是从服务器堆栈定位到未捕获的 `socket.timeout`，在后端把它转换为 API 错误，再调整前端超时窗口并过滤 HTML。升级后又把失败样本、耗时和错误类型写入评测报告，避免把“请求失败”误读成“模型质量差”。这个过程让我形成了从现象、堆栈、接口到用户体验逐层定位的习惯。

### 6. 请举例说明一次失败，以及你学到了什么。

**回答：**

第一次真实 AI 请求的客户端超时时间短于模型实际响应时间，后端完成处理时客户端已经断开，日志出现 `Broken pipe`。这说明只看服务端成功是不够的，端到端超时必须统一设计。我随后把后端和前端超时窗口对齐，并把超时错误纳入测试和进度记录。以后接入外部服务时，我会在一开始就明确总时限、重试次数和用户提示。

### 7. 请举例说明你如何适应变化。

**回答：**

项目从本地演示逐步增加了真实 AI、JWT、消息和地图需求。如果一次性替换所有本地逻辑，容易破坏原有演示和测试。因此我保留 `local-demo/api` 双模式，把 API 调用集中到 `services/api.js`，页面根据模式选择数据源。这样需求变化时可以逐步迁移，也能随时用本地模式回归核心交互。

### 8. 为什么你想加入宝洁？这个项目与宝洁有什么联系？

**回答：**

我希望加入一个重视消费者洞察、执行质量和跨团队协作的组织。团团团让我把“用户说不清需求”转成可以验证的条件，并在推荐、地图和发布流程中持续检查用户是否真正完成任务。宝洁的品牌和产品工作同样需要从消费者场景出发，把洞察转成清晰方案，再通过协作和执行落地。我希望把这种用户视角、结构化拆解和结果复盘能力带到更大规模的业务中。

## 七、面试官可能追问

### 为什么不用 AI 直接生成活动？

因为活动价格、时间、容量和地点是事实字段，应该来自数据库或审核流程。AI 负责理解需求和解释推荐，不负责创造供给。

### 为什么高德 Key 不放前端？

小程序包可以被反编译，前端暴露 Key 容易被滥用。当前由后端代理地点搜索和地址解析，Key 放在 `backend/.env`。

### 当前地图是不是高德底图？

不是。当前地图页使用微信原生 `<map>`，底图由微信地图提供；地点搜索和地址解析使用高德 Web API。这是在本地小程序无需暴露高德 Key、又能快速获得缩放拖动能力之间的折中方案。

### 真实登录是否已经完成？

后端微信配置已经读取，认证代码和 JWT 已完成；还需要在微信开发者工具中触发一次真实 `wx.login`，确认 `/api/v1/auth/wechat/` 返回 200，才能标记真实登录验收完成。

## 八、建议面试表达原则

1. 先说用户问题和结果，再讲技术细节。
2. STAR 中的结果使用可验证事实：测试通过、接口状态、响应时间和数据边界。
3. 明确区分“代码已完成”“真实服务已调用”“模拟器点击已验收”。
4. 不把示例活动、待审核需求或本地演示身份描述为真实商业交易。
